## 想法开工是什么

**想法开工是一套面向非技术用户的 AI 产品开发工具包，由[汪泽雨](https://github.com/wangzeyu846-dot)维护。** 它把需求整理、分阶段开发、结果验收和进度记录组织在一个项目文件夹里，交给能操作本地文件的编码 AI 执行。

你可以从一句话开始：谁遇到了什么问题，你想让哪件事变得更容易。AI 会帮你把想法整理成需求，缩小第一版范围，再逐步实现可以在自己电脑上试用的网页产品。等核心功能和界面确认可用后，再按需要选择上线。

这个项目关注的是开发过程里几个具体的难题：**不知道从哪开始、说不清第一版做什么、看不懂 AI 的技术问题，以及无法判断“做完了”是否可信。** 想法开工为这些时刻提供对应的规则、手册和检查步骤，让你始终知道当前在做什么、接下来需要判断什么。

## 适合谁用

| 你现在的情况 | 可以怎样使用 |
| --- | --- |
| 产品经理，有需求但缺少开发支持 | 把一个核心场景做成可体验的第一版，用实际操作补充产品判断 |
| 创业者，想先验证一个小方向 | 缩小范围，先看产品能否解决具体问题，再决定是否继续投入 |
| 运营、内容或业务同学，熟悉重复工作 | 从手头的真实任务出发，探索资料整理、内容处理等小工具 |
| 正在学习 AI 产品实践 | 在同一个项目里经历需求、实现、验证和反馈，保留可复查的过程 |

你需要了解自己的问题，愿意看结果、给反馈。完整的需求文档、技术方案和产品名字都可以在过程中逐步确定。

当前支持范围是 **Mac 上的网页 MVP**，也就是用较小范围验证核心用途的第一版产品。Windows 尚未验证；大型系统和公开商业运营需要进一步评估。

## 三步开工

### 1. 下载并解压

在本仓库页面点击 **Code → Download ZIP**，将下载的文件解压。也可以前往[版本发布页](https://github.com/wangzeyu846-dot/idea-kickoff/releases/latest)下载已整理的工具包。

解压后的整个文件夹就是工作空间，产品目录和后续文件由 AI 创建。

### 2. 用编码 AI 打开文件夹

准备一个**能读写本地文件、执行命令**的编码 AI 工具，完成安装和账号配置，然后用它打开工具包文件夹。工具包提供 `AGENTS.md` 规则卡和 `CLAUDE.md` 入口，具体操作可看[新手使用指南](./开始看这里.md)。

开工前，AI 会检查 Python、Node.js 和 Git。缺少环境时，它应给出“去哪下载、点什么、看到什么算对”的步骤。

### 3. 说出一个真实问题

例如，把下面这句话发给 AI：

```text
我经常要把几份零散资料整理成报告，来回复制很费时间。
我想做一个小工具，先在自己的电脑上试用，帮我开始。
```

AI 默认只问当前最关键的 **1—3 个业务问题，每轮最多 5 个**，并给推荐理由。你可以回答“不确定”或“按推荐”；需求文档由 AI 整理。已有需求、设计稿、参考截图或评测样例，可以直接交给它复用。

需要明确指定规则时，说“请读取 AGENTS.md，按启动流程开始”。以后再打开同一文件夹，说“继续做 XX”，AI 会读取已有进度。也可以双击 `开工.command`，按窗口提示选择编码工具；两种入口使用同一套流程。

## 从一个小任务开始

下面是适合从小范围验证的产品方向，具体功能与效果需要在各自的产品里实现和验证：

| 产品方向 | 可以先验证的一件事 |
| --- | --- |
| 资料整理助手 | 把几份指定资料整理成结构统一的摘要，检查关键信息是否遗漏 |
| 内容初稿工具 | 根据明确的输入生成一份可修改初稿，判断是否减少了重复起草时间 |
| 用户反馈归纳工具 | 将一批反馈按问题分类，查看归纳是否准确、是否便于后续处理 |
| 业务知识问答助手 | 围绕一组已授权资料回答问题，检查依据是否可靠、资料不足时是否说明边界 |

第一次开工时，可以先选一个用户、一种输入、一个有用的结果。AI 会据此提出第一版范围，并把后续想法记下来。

## AI 做什么，你做什么

| 工作 | AI 负责 | 你负责 |
| --- | --- | --- |
| 说清需求 | 整理想法和已有材料，补充当前必要的问题 | 说明谁遇到问题、现在怎么做、什么结果有用 |
| 确定第一版 | 提出范围、实现建议和分步计划 | 确认理解，判断暂缓哪些功能、能接受哪些成本 |
| 实现与验证 | 写代码、跑检查，整理真实样例与结果 | 按指引配置必要账号或密钥，判断结果是否合格 |
| 做可用界面 | 实现页面，检查电脑与手机宽度 | 给视觉方向，实际操作并反馈 |
| 按需上线 | 核对平台条件与费用，部署并准备验收 | 完成本人授权、确认费用，核对线上使用情况 |
| 继续改进 | 保存反馈和进度，提出最小改动与验证办法 | 指出实际使用中最值得先改的一件事 |

创建目录、改文件、整理文档和执行检查由 AI 完成。需要你操作时，它应说清楚“去哪、点什么、填什么、看到什么算对”。

## 一轮开发怎样推进

**整理想法 → 确定范围 → 验证核心功能 → 完成界面 → 按需上线 → 收尾与改进**

每一阶段只处理当前已确认的范围。AI 准备好实现与证据，完成当前版本自检后，你再按清单体验并明确说“验收通过”，才能进入下一阶段。你不需要填写技术阶段编号。

本轮可以只做本地试用。需要让别人访问时，再确认上线方案与费用。中途暂停后，进度和决定会保存在项目文件中；重新开始时，AI 从记录继续，复用已有材料和仍然有效的决定。

## 你会拿到什么

按已确认的交付范围完成后，产品文件夹会保留：

- **清楚的需求与范围**：目标用户、核心任务、第一版标准，以及暂缓的功能。
- **产品代码和使用方法**：如何启动、如何验证；选择并完成上线时，提供访问地址。
- **可以核对的验收材料**：截图、操作清单、检查结果，以及适用阶段的真实模型调用记录。
- **可接续的进度记录**：当前阶段、已定决策、待验证项和下一步，便于隔天继续或换工具协作。

一个工具包可以放多个产品，每个产品有自己的文件夹、需求和进度。告诉 AI“我要做一个新产品，叫 XX”，它会按目录规则安排。

## 怎样判断真的做对了

每个阶段的验收材料都放在对应产品的 `docs/evidence/` 中，由 AI 和脚本维护。你主要看三件事：能否照清单操作、真实结果是否达到约定标准、还有哪些项没有验证。

检查结果明确区分“通过”“待验”“不通过”和“不适用”。缺少真实模型调用、必要材料或有效检查时，应保留待验状态。代码、提示词、需求或样例变动后，要重新核验当前版本，旧成功不能直接作为新版本的结果。

自检可以减少遗漏，产品是否有用仍需要你的判断。你可以直接问：“这项结论的证据在哪？”试用后，把最费劲的地方告诉 AI，它会复用已有需求和样例，围绕最小改动继续验证。

## 使用条件与当前状态

编码 AI 工具的订阅、产品调用模型的费用和云资源费用可能分别产生。需要付费的云资源应先说明用途和预估费用，再由你确认。模型密钥按指引放在安全位置，不发到对话、不写进仓库。

默认部署路径为腾讯云开发 CloudBase，实际部署前由 AI 核对当时的平台条件、价格、账号要求和已有资源。规则要求重要数据可恢复、上线后用户只能访问自己的数据；这些都需要在实际产品中验证。

截至 **2026-11-18**，工具包的验证范围如下：

| 验证项目 | 当前状态 |
| --- | --- |
| 工具包离线回归 | **55 项通过**，覆盖版本变化、失败与中断、阶段推进、项目恢复及检查缺项等路径 |
| Shell 语法与独立代码评审 | 已完成 |
| 真实模型效果 | **待验证**，需结合实际产品与真实样例检查 |
| 云端部署 | **待验证**，需按实际产品完成上线验证 |
| 非技术用户的上手体验 | **待真实用户试用** |

离线测试中的产品测试和包管理命令使用隔离替身，文件检查、流程推进和进程恢复路径实际执行。离线结果不能代替真实模型效果或用户价值判断。
